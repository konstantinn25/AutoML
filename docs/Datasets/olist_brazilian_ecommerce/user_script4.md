# OL-04 - Временная проверка прогноза просрочки с ограничением обучения

**Датасет:** Olist Brazilian E-Commerce (девять связанных CSV)  
**Категория:** явный, ограничения, временная валидация  

## 1. Входные данные

**Запрос пользователя:**

> «Подготовь прогноз просрочки `late_delivery`, метрика `roc_auc`, на обучение десять минут. Для проверки возьми более поздние заказы по дате покупки. Убедись, что к началу проверяемого периода исходы обучающих заказов уже известны. После обучения покажи сравнение моделей.»

**Вход для будущего теста:** исходные таблицы Olist, включая `olist_orders_dataset.csv` и таблицы товаров, покупателей и продавцов, вместе с приведённым выше текстом.

## 3. Ручное решение и конфигурация

- **Задача и таргет:** Подготовить одну строку на заказ и сформировать `late_delivery` по календарным датам обещанной и фактической доставки. Для 96 470 заказов метка определена; положительный класс `1` встречается у 6 534 заказов (6,77%). После проверки витрины использовать `label = "late_delivery"`, `problem_type = "binary"`, `positive_class = 1`.
- **Метрика и бюджет:** Пользователь явно назначил `eval_metric = "roc_auc"` и `time_limit = 600` секунд. Эти ограничения относятся к обучению и выбору моделей в AutoGluon; длительность подготовки девяти таблиц и расчёта итогового отчёта в лимит `fit()` автоматически не входит. Не менять метрику на `accuracy` из-за дисбаланса.
- **Подготовка признаков:** Исходные таблицы имеют связи один-ко-многим, поэтому агрегировать позиции и другие необходимые дочерние сведения до уровня `order_id`. Проверить уникальность заказов после объединения. Момент прогнозирования не задан: для базового варианта прогноза при оформлении использовать только признаки, доступные к покупке. Поля фактической доставки, итогового статуса, отзывов и неподтверждённо готовых платежей исключить. Если предполагается другой момент, согласовать правила доступности.
- **Хронологическое разделение:** Разделить заказы по `order_purchase_timestamp`, чтобы независимая тестовая часть содержала более поздние покупки. В EDA показана иллюстративная граница `2018-05-26 18:18:03`: до фильтра готовности меток получено 77 176 ранних заказов, после фильтра по завершению доставки до границы - 75 128; в более поздней оценочной части - 19 294 заказа с известной в итоге меткой. Числа иллюстративны, выбранная граница не задана пользователем и должна фиксироваться в протоколе.
- **Доступность исходов и внутренняя валидация:** Метка обучающего заказа должна существовать на момент соответствующего обучения, а не быть известной лишь задним числом. Тестовые ответы нельзя использовать при настройке моделей, отборе признаков или выборе порога. Внешнее временное разделение не делает автоматически корректной внутреннюю валидацию AutoGluon: её нужно согласовать с выбранной стратегией или сообщить об ограничении. Повторные `customer_unique_id` между периодами допустимы для проверки будущих заказов, но такой тест не доказывает обобщение на совершенно новых покупателей.
- **Выдача результатов:** Установить `return_leaderboard = true` в настройках сервиса. Это не аргумент `fit()`. Для оценки на тестовых заказах использовать данные с известными ответами и корректно интерпретировать `roc_auc`.

**Кандидат конфигурации** (условный, после подготовки витрины и определения корректной схемы внутренней временной валидации):

```json
{
  "label": "late_delivery",
  "problem_type": "binary",
  "positive_class": 1,
  "eval_metric": "roc_auc",
  "ignored_columns": [
    "order_id"
  ],
  "validation_procedure": "auto",
  "time_limit": 600,
  "presets": "medium_quality"
}
```

В отдельной конфигурации выдачи результатов требуется `return_leaderboard = true`. При сохранении `order_id` в подготовленной таблице его исключает обёртка; если он удалён раньше, `ignored_columns` корректируется. Значение `validation_procedure = "auto"` не гарантирует соблюдение хронологии внутренней валидации. До запуска необходимо выбрать совместимую с временной постановкой схему обучения; при невозможности её обеспечить запуск с заявленной корректной временной оценкой останавливается.

## 4. Критерии проверки агента

- **Обязательные результаты:** агент определяет бинарную цель `late_delivery` и положительный класс `1`, устанавливает `eval_metric=roc_auc`, `time_limit=600`, требует хронологический внешний тест по дате покупки с доступными к границе метками, агрегирует связанные таблицы и использует `return_leaderboard=true` как настройку сервиса.
- **Допустимые альтернативы:** другая обоснованная дата границы при сохранении хронологии и доступности меток; запрос уточнения о моменте прогнозирования; иная реализация внутренней временной валидации при доказанной корректности; указание на ограничение применимости к заказам, завершившимся доставкой.
- **Критические ошибки:** перемешать заказы для независимого теста вопреки запросу; включить в обучение исходы, неизвестные к началу тестового периода; применить фактическую доставку или отзывы как ранние предикторы; размножить заказы при соединении; забыть `time_limit=600` или `roc_auc`; передать `return_leaderboard` напрямую в `fit()`; считать `validation_procedure=auto` гарантией правильной временной внутренней валидации.
