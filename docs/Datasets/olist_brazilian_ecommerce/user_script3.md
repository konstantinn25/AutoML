# OL-03 - Ошибочная разметка неизвестных исходов и соединение таблиц

**Датасет:** Olist Brazilian E-Commerce (девять связанных CSV)  
**Категория:** ошибочная разметка, ошибочное соединение  

## 1. Входные данные

**Запрос пользователя:**

> «Если заказ отменили или он пока в пути, запиши для late_delivery ноль. Раз доставки с опозданием не было, значит всё хорошо. И просто склей товары, платежи и отзывы с orders как есть.»

**Вход для будущего теста:** исходные девять CSV Olist, в том числе `olist_orders_dataset.csv`, `olist_order_items_dataset.csv`, `olist_order_payments_dataset.csv`, `olist_order_reviews_dataset.csv`, вместе с приведённым выше текстом.

## 2. Ручной анализ запроса

Результат извлечения требований из текста:

```json
{
  "goal": {
    "value": "присвоить отменённым и ещё доставляемым заказам метку late_delivery=0 и напрямую объединить таблицы заказов, товаров, платежей и отзывов",
    "status": "explicit"
  },
  "task_type": {
    "value": null,
    "status": "unknown"
  },
  "target": {
    "value": "late_delivery",
    "status": "explicit"
  },
  "metric": {
    "value": null,
    "status": "unknown"
  },
  "constraints": {
    "training_time": {
      "value": null,
      "status": "unknown"
    }
  },
  "requirements": {
    "target_labeling": {
      "value": "для отменённых и находящихся в пути заказов установить late_delivery=0",
      "status": "explicit"

    "data_joining": {
      "value": "соединить товары, платежи и отзывы с orders без предварительной агрегации",

```

Пользователь прямо задаёт правила подготовки данных и называет будущий столбец `late_delivery`. Самостоятельную задачу обучения, момент прогнозирования и метрику он не формулирует. Внутри запроса противоречий нет. Ошибочность правил обнаруживается после сопоставления с данными и определением просрочки.

## 3. Ручное решение и конфигурация

- **Задача:** Запрос касается подготовки метки и объединения таблиц. Название `late_delivery` указано явно, но пользователь не просит обучить конкретную модель. Самостоятельную ML-конфигурацию не формировать до уточнения задачи и момента применения модели.
- **Разметка:** Для `late_delivery` сравнивать календарную дату фактической доставки с обещанной только при известном исходе. В EDA получено 96 470 размеченных заказов: 6 534 поздних и 89 936 без просрочки. Всего 2 971 заказ не имеет допустимой метки в выбранной постановке. Отмена и доставка, ещё не завершившаяся на дату наблюдения, не являются доказательством своевременной доставки. Нельзя кодировать такие исходы нулём. При необходимости отмену и просрочку можно рассматривать как разные события, но это потребует новой целевой постановки.
- **Уровень наблюдения:** Базовая таблица `olist_orders_dataset.csv` содержит 99 441 уникальный заказ. В `items` у 9 803 заказов больше одной позиции; в `payments` у 2 961 - больше одного платежа; в `reviews` у 547 - больше одного отзыва. Прямое соединение дочерних таблиц даёт 119 143 строки вместо 99 441. Если суммировать платежи после некорректного соединения с позициями, сумма увеличится на 27,87%; это признак размножения, а не новой выручки.
- **Корректное объединение:** Отдельно агрегировать позиции, сведения о продавцах и при необходимости платежи и отзывы до уровня `order_id`. Затем выполнить контролируемые левосторонние соединения с `orders`, проверить число и уникальность `order_id`, непротиворечивость сумм и охват. Сведения `geolocation` нельзя напрямую соединять по почтовому префиксу без агрегации.
- **Доступность признаков:** Для будущей модели нужно уточнить момент прогнозирования. Если он приходится на оформление заказа, фактические даты доставки, итоговые статусы и отзывы нельзя использовать как предикторы; финальные платежные сведения требуют дополнительного подтверждения. Наличие столбцов в исторических данных не доказывает их доступность при прогнозе.

**Кандидат конфигурации: не формируется.**

Запрос требует исправления правил разметки и соединения таблиц. Без согласования постановки обучения и момента прогнозирования нельзя считать `late_delivery` уже подтверждённым входом для AutoGluon. Допустимо подготовить отчёт о проблемах и безопасный план создания витрины.

## 4. Критерии проверки агента

- **Обязательные результаты:** агент не записывает отменённым и незавершённым заказам метку `0`, различает неизвестный исход и отрицательный класс, проверяет кратности таблиц, сохраняет одну строку на `order_id` после агрегации и не выдаёт подготовку данных за готовую ML-конфигурацию.
- **Допустимые альтернативы:** предложить отдельную категорию для отмен или иную целевую постановку после согласования; подготовить безопасную промежуточную витрину с пропущенными неизвестными метками; описать способы агрегации платежей и позиций с контролем сумм.
- **Критические ошибки:** разметить неопределённые исходы как своевременную доставку; напрямую объединить все дочерние таблицы без проверки кратности; принять размноженные строки за независимые заказы; использовать отзывы как ранние признаки без подтверждения; произвольно сформировать окончательную конфигурацию модели.
