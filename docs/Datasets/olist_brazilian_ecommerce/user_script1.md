# OL-01 - Прогноз просрочки доставки при оформлении заказа

**Датасет:** Olist Brazilian E-Commerce (девять связанных CSV)  
**Категория:** длинный, бизнес-постановка, создание таргета  

## 1. Входные данные

**Запрос пользователя:**

> «У нас интернет-магазин, и клиенты часто жалуются на опоздавшие посылки. Сейчас отчёт считает среднюю скорость доставки, но мне нужен другой результат. Когда человек оформил заказ, хотелось бы сразу предупреждать, есть ли риск, что привезём позже обещанного дня. В файлах заказов полно статусов и дат, а отдельной колонки «опоздал» я не вижу. Можно подготовить такую задачу и научить модель, не подсматривая в фактическую дату доставки?»

**Вход для будущего теста:** девять исходных CSV Olist, включая `olist_orders_dataset.csv`, `olist_order_items_dataset.csv`, `olist_customers_dataset.csv`, и приведённый выше текст.

## 2. Ручной анализ запроса

Результат извлечения требований из текста:

```json
{
  "goal": {
    "value": "предупреждать о риске доставки заказа позже обещанного дня",
    "status": "explicit"
  },
  "task_type": {
    "value": "binary",
    "status": "inferred"
  },
  "target": {
    "value": "факт доставки позже обещанного дня",
    "status": "explicit"
  },
  "metric": {
    "value": null,
    "status": "unknown"
  },
  "constraints": {
    "training_time": {
      "value": null,
      "status": "unknown"
    }
  },
  "requirements": {
    "prediction_moment": {
      "value": "сразу при оформлении заказа",
      "status": "explicit"
    },
    "target_creation": {
      "value": "подготовить целевую переменную просрочки, поскольку отдельной колонки нет",
      "status": "explicit"
    },
    "feature_availability": {
      "value": "не использовать фактическую дату доставки как предиктор",
      "status": "explicit"
    }
  },
  "conflicts": []
}
```

Пользователь формулирует бизнес-цель и момент прогноза, но не называет конкретные столбцы, метрику и бюджет. Бинарная постановка следует из противопоставления своевременной и поздней доставки. Внутренних противоречий нет.

## 3. Ручное решение и конфигурация

- **Задача и целевая переменная:** Создать витрину с одной строкой на `order_id`. Для доставленных заказов с известными `order_delivered_customer_date` и `order_estimated_delivery_date` сформировать `late_delivery = 1`, если календарная дата фактической доставки позже обещанной календарной даты; иначе `0`. Сравнивать именно даты, а не timestamp с полуночью у обещанного срока. После подготовки выбрать `label = "late_delivery"`, `problem_type = "binary"`, `positive_class = 1`.
- **Наличие меток:** В EDA метка определена для 96 470 заказов, из них 6 534 (6,77%) имеют просрочку. Из всех 99 441 заказов для данной постановки не размечены 2 971. Отменённые и незавершённые заказы нельзя автоматически считать доставленными в срок. Обучение только по завершённым доставкам создаёт ограничение применимости модели ко всем будущим покупкам.
- **Подготовка данных:** Объединять заказы с покупателями и агрегатами товаров на уровне `order_id`. Позиции, платежи и отзывы могут содержать по нескольку записей на заказ. Прямое соединение размножит строки; для геолокации требуется отдельная агрегация по почтовому префиксу. Категории, стоимости и характеристики товара использовать только после проверки доступности в момент оформления.
- **Признаки:** Фактическую доставку и рассчитанную метку использовать для обучения как информацию об исходе, но не в качестве входных признаков. Не передавать в модель `order_delivered_customer_date`, поздние статусы, сведения о передаче перевозчику и отзывы. Доступность обещанной даты, финальных платежей и характеристик заказа на момент покупки проверить отдельно. Идентификаторы сохранять для соединения и контроля разбиения, но исключать из предикторов.
- **Метрика и валидация:** Пользователь не указал стоимость пропущенной просрочки и ложного предупреждения. Для исходного сравнения моделей допустима `roc_auc`; это решение системы, а не извлечённая метрика. С учётом дат покупки использовать хронологическую независимую проверку. К началу оценочного периода метки обучающих заказов должны быть уже известны. Отдельно учитывать возможное повторение `customer_unique_id` между периодами.

**Кандидат конфигурации** (условный, после формирования витрины, подтверждения доступности признаков и выбора корректной внутренней валидации):

```json
{
  "label": "late_delivery",
  "problem_type": "binary",
  "positive_class": 1,
  "eval_metric": "roc_auc",
  "ignored_columns": [
    "order_id"
  ],
  "validation_procedure": "auto",
  "presets": "medium_quality"
}
```

`order_id` остаётся в подготовленной витрине для связи с заказом и исключается из признаков через обёртку. Если идентификатор удалён ещё до обучения, передавать его в `ignored_columns` не нужно. Остальные недоступные на момент покупки столбцы должны быть исключены при создании витрины. `validation_procedure = "auto"` не заменяет временное внешнее разбиение и само по себе не гарантирует корректную временную внутреннюю валидацию. Лимит `time_limit` устанавливается сервисом по умолчанию.

## 4. Критерии проверки агента

- **Обязательные результаты:** агент выделяет просрочку доставки как бинарную задачу, создаёт метку сравнением календарных дат, отличает метку от признаков, не допускает фактическую доставку и отзывы в предикторы при оформлении заказа, агрегирует связанные таблицы до уровня заказа и учитывает неизвестные исходы.
- **Допустимые альтернативы:** другая обоснованная метрика бинарной классификации; запуск на ограниченном наборе подтверждённо доступных признаков; запрос уточнения о доступности обещанной даты или моменте окончательного подтверждения сведений; отдельная оценка смещения из-за отбора доставленных заказов.
- **Критические ошибки:** считать просрочкой доставку в тот же обещанный календарный день из-за сравнения времени суток; размечать отменённые и ещё не доставленные заказы нулём без подтверждения; использовать реальные даты доставки, отзывы или поздние статусы как ранние признаки; напрямую соединять дочерние таблицы с размножением `order_id`; считать `roc_auc` прямо названной пользователем.
