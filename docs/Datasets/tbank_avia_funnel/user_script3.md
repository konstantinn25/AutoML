# TA-03 - Прогноз после поиска с использованием будущих экранов

**Датасет:** Т-Банк: Воронка авиабилетов (`dano_dataset_avia_hashed_corrected_s.xlsx`)  
**Категория:** момент прогнозирования, утечка, ошибочная валидация  

## 1. Входные данные

**Запрос пользователя:**

> «Нужна оценка покупки сразу после экрана поиска. Вся таблица действий у нас есть, поэтому для каждого захода собери количество всех экранов вплоть до «Покупка бэк» - чем больше данных, тем лучше. Тест сделай случайно по строкам Excel.»

**Вход для будущего теста:** исходный `dano_dataset_avia_hashed_corrected_s.xlsx` и приведённый выше текст. Проверяются граница доступности событий и независимость тестовой выборки.

Случайное разделение строк Excel - отдельное требование; его некорректность для сессионных данных устанавливается после изучения структуры датасета.

## 3. Ручное решение и конфигурация

- **Задача и таргет:** Предполагается бинарная классификация сессий по последующей успешной покупке. На уровне исходных событий готовой сессионной метки нет. Для положительного класса использовать подтверждённый статус `Успешные`; для отрицательного необходимо согласовать правила регистрации исходов. Без подтверждения отрицательных меток финальное обучение откладывается.
- **Конфликт признаков:** Для прогноза после поиска допустима только информация, полученная к выбранной точке среза. Экран `Покупка бэк` относится к последующим стадиям; все 2 622 события с подтверждённым успехом зафиксированы именно на нём. Полное число посещений экранов и поля `session_purchase_*` раскрывают дальнейшие действия. Их нельзя использовать в предикторах раннего прогноза. Предложить ограничить признаки доступной историей либо перенести момент прогноза с новой формулировкой задачи.
- **Формирование среза:** В EDA выявлено 37 756 сессий с экраном `Поиск`, 34 324 - с `Выдача`, 2 507 - с `Покупка бэк`. Внутри сессии экраны могут повторяться. Нужно уточнить, после какого появления экрана поиска строится прогноз, и сформировать одну запись на `session_id` по событиям не позднее соответствующего времени. Не использовать итоговые количества экранов за всю сессию даже при высокой связи с покупкой.
- **Тестовое разбиение:** Исходные 244 345 строк относятся к 38 561 сессии; у 34 522 сессий больше одного события. Случайное разделение исходных строк может поместить события одной сессии и в train, и в test. Сначала подготовить сессионные наблюдения, затем выделить независимые части. Для проверки будущих сессий использовать хронологию начала сессии; для проверки новых клиентов - разделение по `client_id` без пересечений. Выбор внутренней валидации AutoGluon также должен соответствовать постановке.
- **Метрика и ограничения:** После подготовки корректных меток можно рассмотреть `roc_auc` с дополнительными `precision` и `recall`. Метрика и вычислительный бюджет в запросе отсутствуют; не приписывать их пользователю. Доля 6,13% относится к подтверждённым покупкам среди всех сессий, а не к проверенному распределению классов обучающей выборки.

**Кандидат конфигурации: не формируется.** До устранения конфликта о признаках, отказа от разделения исходных строк и согласования отрицательных меток запуск не может считаться корректным. Агент может предложить план построения сессионной витрины и допустимых вариантов проверки.

## 4. Критерии проверки агента

- **Обязательные результаты:** агент выявляет внутреннее противоречие между ранним прогнозом и поздними экранами, отказывается включать `Покупка бэк` и полные счётчики событий в признаки, требует формировать одну строку на сессию и отвергает случайное деление строк исходного Excel. Отдельно сообщает о неопределённости отрицательных меток и предлагает корректные варианты тестирования.
- **Допустимые альтернативы:** уточнить точный момент после поиска, особенно при повторных экранах; предложить прогноз на более позднем этапе с пересмотром задачи; использовать обоснованное сессионное разбиение с дополнительной временной или групповой проверкой при соответствии цели применения.
- **Критические ошибки:** включить последующие экраны и поля `session_purchase_*` в раннюю модель; случайно разделить исходные события и выдавать результат за независимый тест по сессиям; использовать технический `session_id` как таргет; приравнять все сессии без успеха к отказам; выдать готовую конфигурацию, не разрешив конфликт и отсутствие надёжных отрицательных меток.
