# TA-01 - Прогноз покупки авиабилета в начале сессии

**Датасет:** Т-Банк: Воронка авиабилетов (`dano_dataset_avia_hashed_corrected_s.xlsx`)  
**Категория:** короткий, формирование таргета  

## 1. Входные данные

**Запрос пользователя:**

> «Можно по началу захода в Авиабилеты понять, купит человек билет или просто посмотрит?»

**Вход для будущего теста:** исходный `dano_dataset_avia_hashed_corrected_s.xlsx` и приведённый выше текст. В файле содержатся события экранов; таблицу на уровне сессий предстоит подготовить отдельно.

## 2. Ручной анализ запроса

Результат извлечения требований из текста:

```json
{
  "goal": {
    "value": "в начале посещения сервиса оценивать, завершится ли сессия покупкой авиабилета",
    "status": "explicit"
  },
  "task_type": {
    "value": "binary",
    "status": "inferred"
  },
  "target": {
    "value": "факт покупки авиабилета в рамках посещения сервиса",
    "status": "explicit"
  },
  "metric": {
    "value": null,
    "status": "unknown"
  },
  "constraints": {
    "training_time": {
      "value": null,
      "status": "unknown"
    }
  },
  "requirements": {
    "prediction_moment": {
      "value": "в начале сессии, до дальнейшего прохождения экранной воронки",
      "status": "explicit"
    },
    "prediction_scope": {

```

Пользователь описывает покупку как бинарный исход и прямо задаёт ранний момент прогноза. Названия исходных столбцов, метрика и ограничения обучения не указаны. Смысл «просто посмотрит» ещё не подтверждает правило определения отрицательного класса. Внутренних противоречий нет.

## 3. Ручное решение и конфигурация

- **Задача и таргет:** Единицей наблюдения должна быть сессия `session_id`, а не строка посещения экрана. В EDA обнаружены 244 345 событий и 38 561 сессия. Создать в подготовленной сессионной таблице бинарную метку, например `purchase_success`: `1` для подтверждённой успешной покупки. Такой колонки нет в исходном Excel. Положительных сессий по статусу `Успешные` - 2 364 (6,13% всех сессий). Это доля подтверждённого успеха, а не установленная доля покупок среди полностью размеченных исходов.
- **Отрицательные и неопределённые исходы:** Для 143 сессий указана цена покупки, но отсутствует подтверждённый статус. У 36 054 сессий нет ни подтверждённого успеха, ни цены. Ни одну из этих групп нельзя без проверки полноты регистрации исходов автоматически считать отказом от покупки. Запросить правило определения завершённой сессии и отрицательной метки; при отсутствии такого правила корректная размеченная бинарная выборка не готова.
- **Признаки и момент прогноза:** Агрегировать данные до одной записи на `session_id`, используя только сведения, известные при начале сессии: дату и время начала, устройство, источник и канал, если они доступны сразу. Данные о клиенте (`client_segment`, `client_gmv`, `client_avia_orders`) допустимы лишь после подтверждения, что они отражают состояние до начала данной сессии. Исключить последующие посещения экранов, счётчики полной сессии и поля `session_purchase_*`. `session_id` и `client_id` использовать как технические ключи, а не как предикторы.
- **Метрика:** После формирования обеих меток допустима `roc_auc` как предварительная метрика ранжирования. Из-за редкого подтверждённого положительного исхода отдельно оценивать `precision`, `recall` и выбор порога, если модель применяется для действий. Метрика не указана пользователем и выбирается на этапе конфигурирования.
- **Валидация:** Для оценки на будущих посещениях предпочтительно независимое хронологическое разбиение по началу сессии. В EDA рассмотрена иллюстративная граница `01.08.2025`; её нельзя автоматически считать утверждённой границей теста. Не делить исходные события случайно, чтобы одна сессия не попадала в обучение и тест одновременно. При проверке новых клиентов дополнительно требуется разделение по `client_id`. Внутренняя валидация AutoGluon тоже должна учитывать выбранную структуру данных.

**Кандидат конфигурации** (только после согласования отрицательных меток, построения сессионной таблицы и проверки доступности признаков):

```json
{
  "label": "purchase_success",
  "problem_type": "binary",
  "positive_class": 1,
  "eval_metric": "roc_auc",
  "ignored_columns": [
    "session_id",
    "client_id"
  ],
  "validation_procedure": "auto",
  "presets": "medium_quality"
}
```

`purchase_success` - предлагаемое имя нового столбца, а не поле исходного файла. Если технические идентификаторы удалены до обучения, `ignored_columns` корректируется. `validation_procedure = "auto"` не обеспечивает автоматически корректную временную внутреннюю валидацию. `time_limit` задаётся сервисом по умолчанию. До подтверждения отрицательных меток и состава ранних признаков конфигурацию нельзя считать готовой к запуску.

## 4. Критерии проверки агента

- **Обязательные результаты:** агент выделяет прогноз покупки в начале сессии, выводит `binary`, предлагает сессионный таргет, использует статус `Успешные` только для подтверждённых положительных исходов, отдельно разбирает 143 неоднозначные сессии и неизвестные отрицательные исходы. Не допускает поздние экраны и покупочные поля в ранние признаки, не выдаёт условный JSON за готовую конфигурацию.
- **Допустимые альтернативы:** другое имя производного таргета; уточнение горизонта и признаков завершённой сессии; выбор другой обоснованной бинарной метрики после подтверждения меток; временное исключение сессий с неопределённым исходом при явно обоснованной процедуре, обеспечивающей репрезентативность оставшейся выборки.
- **Критические ошибки:** трактовать все 36 197 сессий без подтверждённого успеха как доказанные отказы; принимать наличие цены за подтверждённую покупку; обучаться на отдельных строках экранов вместо сессий; использовать `session_purchase_status`, `session_purchase_price` или поздние экраны при прогнозе на входе; объявлять 6,13% окончательной долей положительного класса в размеченной выборке; запускать модель без корректных отрицательных примеров.
