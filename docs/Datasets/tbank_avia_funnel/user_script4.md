# TA-04 - Проверка покупок у новых клиентов с ограничениями обучения

**Датасет:** Т-Банк: Воронка авиабилетов (`dano_dataset_avia_hashed_corrected_s.xlsx`)  
**Категория:** длинный, ограничения, групповая валидация  

## 1. Входные данные

**Запрос пользователя:**

> «Хочу проверить, как модель выявляет покупки у клиентов, которых раньше не было в нашей истории. Обучение - не более пяти минут, GPU отключить. Для исхода используй подтверждённый статус «Успешные», после обучения покажи важность признаков. Но если часть сессий нельзя честно считать отказами, сначала объясни, что с ними делать.»

**Вход для будущего теста:** исходный `dano_dataset_avia_hashed_corrected_s.xlsx` и приведённый выше текст. События необходимо агрегировать до сессий, сохранив `client_id` для независимого разбиения по клиентам.

## 3. Ручное решение и конфигурация

- **Задача и таргет:** Предлагается бинарная классификация на уровне `session_id` с положительным классом `1`. Создать производную метку, например `purchase_success`, где `1` означает наличие в сессии статуса `Успешные`. В EDA подтверждено 2 364 таких сессии из 38 561. Для остальных исходов окончательных отрицательных меток нет: 143 сессии имеют цену без успеха, 36 054 - ни статуса, ни цены. До обучения требуется согласовать порядок их разметки или получение дополнительных подтверждений.
- **Групповая проверка:** В данных 1 900 уникальных `client_id`, каждый клиент представлен несколькими сессиями. Для независимого теста на клиентах, не встречавшихся в обучении, разделять данные по `client_id`, а не случайно по событиям или сессиям. Проверить достаточное число положительных примеров в каждой части после формирования меток. Если требуется одновременно тестировать более поздние периоды и новых клиентов, дополнительно согласовать временную границу; групповой тест сам по себе не доказывает качество на будущих датах.
- **Момент и признаки:** Пользователь не уточнил, прогноз делается в начале сессии или на одном из экранов. Перед подготовкой признаков необходимо определить этот момент. `session_purchase_status`, `session_purchase_price`, `session_purchase_tickets_num` и последующие экраны использовать только для формирования исхода, но не как предикторы раннего прогноза. `client_id` хранить для разбиения, но не включать в признаки. `client_gmv`, `client_avia_orders` и сегмент нельзя без проверки считать доступными в нужный момент, особенно для новых клиентов: историческая информация для них может отсутствовать.
- **Метрика:** Пользователь не задаёт метрику и соотношение цен ошибок. После получения проверенных положительных и отрицательных меток допустима `roc_auc` для базового сравнения, с дополнительным анализом `precision`/`recall`. Подтверждённые успехи составляют 6,13% всех сессий, но эта доля не является доказанным распределением классов готовой обучающей выборки.
- **Ограничения и результат:** Установить `time_limit = 300`, `num_gpus = 0`. Лимит относится к `fit()`, а не к подготовке 244 345 событий, формированию тестовой выборки, расчёту важности признаков и выдаче отчёта. В отдельных настройках сервиса указать `return_feature_importance = true`; использовать `predictor.feature_importance()` на подходящих оценочных данных после обучения. Важность признака не доказывает причинного влияния на покупку. Не обещать получение отчёта, пока не подготовлены метки и согласована схема обучения.

**Кандидат конфигурации** (условный; допустим только после согласования отрицательных меток, момента прогноза и корректного группового разбиения):


`purchase_success` - новый столбец сессионной витрины, а не готовое поле Excel. `session_id` и `client_id` исключаются из предикторов, если остаются в таблице обучения; иначе список `ignored_columns` сокращается. `validation_procedure = "auto"` не гарантирует корректной внутренней групповой валидации; её требуется обеспечить отдельно либо остановить запуск с предупреждением. `return_feature_importance` - параметр настроек сервиса, а не `fit()`. Пользователь не задавал лимит CPU; его нельзя извлекать из текста. При нерешённых вопросах приведённый JSON не является готовой финальной конфигурацией.

## 4. Критерии проверки агента

- **Обязательные результаты:** агент выделяет бинарную задачу с положительной меткой по `Успешные`, не считает все неподтверждённые исходы отказами, формирует одну строку на сессию и проверяет новых клиентов разбиением по `client_id`. Устанавливает `time_limit=300` и `num_gpus=0`, требует уточнить момент прогноза, отделяет `return_feature_importance=true` от конфигурации обучения и объясняет ограничение по времени расчёта отчёта.
- **Допустимые альтернативы:** дополнительная временная проверка при соблюдении групповых ограничений; другая обоснованная метрика после согласования отрицательных исходов; согласованное исключение неопределённых наблюдений или получение уточнённых статусов, если обеспечена корректность обучающей популяции; другой способ представления важности признаков, не выдающий корреляцию за причинность.
- **Критические ошибки:** разделить события или сессии случайно и заявить проверку на новых клиентах при пересечении `client_id`; автоматически присвоить нули 36 197 неподтверждённым исходам; использовать будущие экраны или поля покупки как признаки без определения момента прогноза; игнорировать `time_limit=300` и `num_gpus=0`; передать `return_feature_importance` напрямую в `fit()`; объявить `validation_procedure=auto` достаточным для групповой валидации или запустить обучение без проверенных отрицательных меток.
