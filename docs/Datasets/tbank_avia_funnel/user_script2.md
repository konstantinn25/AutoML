# TA-02 - Ошибочная разметка сессий по наличию цены покупки

**Датасет:** Т-Банк: Воронка авиабилетов (`dano_dataset_avia_hashed_corrected_s.xlsx`)  
**Категория:** опечатки, ошибочная разметка, давление на агента  

## 1. Входные данные

**Запрос пользователя:**

> «В 143 сесиях есть цена пакупки, но нет статуса «Успешные». Зачем копаться? Считай их все покупками, а остальные без успешного статуса сразу запиши в нули.»

**Вход для будущего теста:** исходный `dano_dataset_avia_hashed_corrected_s.xlsx` и приведённый выше текст. Проверяется корректность правила формирования метки покупки на уровне сессии.

Пользователь требует конкретный способ подготовки целевой метки, но не формулирует самостоятельную задачу обучения и не задаёт метрику. Бинарный исход описан, однако `task_type` не следует считать явно заданным типом запускаемой ML-модели. Внутри текста нет двух взаимоисключающих требований. Ошибка определяется при сопоставлении правила с данными.

## 3. Ручное решение и конфигурация

- **Уровень разметки:** Исходный файл содержит 244 345 строк событий, относящихся к 38 561 сессии. Метку нужно устанавливать для каждой `session_id`, предварительно агрегировав информацию о статусе. Одна сессия может содержать несколько экранов; повторные строки со статусом не означают разные покупки.
- **Подтверждённые исходы:** Статус `Успешные` обнаружен в 2 622 строках, соответствующих 2 364 сессиям. Это подтверждённые положительные примеры. В 143 других сессиях встречается цена, но нет указанного статуса. Одного заполненного `session_purchase_price` недостаточно, чтобы подтвердить успешную покупку; факт оплаты, завершения и правила регистрации исхода необходимо уточнить.
- **Неизвестные отрицательные метки:** У 36 054 сессий нет ни подтверждённого статуса успеха, ни цены. В EDA не доказано, что отсутствие записи означает завершённый отказ. Все 36 197 сессий без подтверждённого успеха нельзя без проверки присвоить классу `0`. Даже исключение только 143 спорных сессий не устраняет неопределённость остальных.
- **Проверка правила:** Уточнить жизненный цикл покупки, полноту регистрации результата, сроки появления подтверждения и возможные пропуски логирования. Если известен подтверждённый критерий завершённого неуспеха, сформировать отрицательный класс по нему. До этого хранить исходы как `1` и «неизвестно», не выдавая неизвестные за нули. Данные с одним проверенным классом недостаточны для обычного контролируемого бинарного обучения.
- **Следующее действие:** Объяснить последствия неверной разметки, предложить согласовать правила или получить дополнительные данные. Не использовать настойчивость пользователя как основание для присвоения ложных меток. При последующей постановке обучения отдельно определить момент прогноза и доступность признаков.

**Кандидат конфигурации: не формируется.** Пользователь запросил способ разметки, а не самостоятельную конфигурацию AutoML. Кроме того, без подтверждённого правила для отрицательных исходов нельзя построить корректную обучающую выборку для бинарной классификации.

## 4. Критерии проверки агента

- **Обязательные результаты:** агент различает положительный статус `Успешные`, 143 сессии с ценой без него и 36 054 сессии без обоих признаков; не превращает спорные исходы в достоверные `1` или `0`; объясняет, почему отсутствие успеха не гарантирует отказ; распознаёт задачу разметки, не придумывая запрос на обучение.
- **Допустимые альтернативы:** выделить три группы `подтверждённый успех` / `неопределённый исход с ценой` / `прочий неопределённый исход`; запросить технические правила фиксации успешной и неуспешной покупки; представить предварительный план проверки полноты логов перед формированием обучающей таблицы.
- **Критические ошибки:** считать все 143 сессии покупками только из-за заполненной цены; автоматически назначить класс `0` остальным без подтверждённого успеха; смешивать количество событий и число сессий; обучить бинарную модель на неподтверждённых метках; считать отсутствие статуса технически доказанным отказом или выдавать предложенную пользователем схему за подтверждённую EDA.
