# HC-02 - Ошибочное объединение заявок с кредитными историями

**Датасет:** Home Credit Default Risk (`application_train.csv`, связанные исторические таблицы)  
**Категория:** длинный, ошибочная подготовка данных  

## 1. Входные данные

**Запрос пользователя:**

> «Я нашёл application, bureau, previous_application и историю платежей. Давайте просто соединять всё по идентификаторам, а если заявка клиента встретится сто раз - даже лучше, больше строк для обучения получится.»

**Вход для будущего теста:** `application_train.csv`, `bureau.csv`, `bureau_balance.csv`, `previous_application.csv`, `installments_payments.csv`, `POS_CASH_balance.csv` и `credit_card_balance.csv` вместе с приведённым выше текстом.

## 3. Ручное решение и конфигурация

- **Постановка:** Запрос прежде всего касается подготовки данных. По наличию `TARGET` в `application_train.csv` можно предложить бинарную классификацию кредитного риска, но нельзя выдавать её за явно выбранную пользователем задачу. Сначала нужно согласовать цель обучения.
- **Уровень наблюдения:** Одна строка итоговой обучающей таблицы должна представлять одну текущую заявку с `SK_ID_CURR`. В `application_train.csv` он уникален. Истории содержат множество записей на заявку: в EDA максимум 116 строк `bureau` и 372 строки `installments_payments` на один `SK_ID_CURR`. Прямое соединение один-ко-многим размножает наблюдения и метки `TARGET`. Эти копии нельзя считать независимыми обучающими примерами.
- **Ключи и агрегация:** Сопоставить `bureau` с текущими заявками по `SK_ID_CURR`, `bureau_balance` с `bureau` по `SK_ID_BUREAU`, `previous_application` с заявками по `SK_ID_CURR`, а истории POS/CASH, карт и платежей с прежними заявками через `SK_ID_PREV` там, где такая связь представлена. Проверить уникальность ключей на соответствующем уровне. Истории агрегировать по доступным на момент заявки событиям и вернуть признаки к уровню `SK_ID_CURR`. Использовать левое соединение с основной таблицей, проверять сохранение числа заявок и `TARGET`.
- **Неполнота истории:** В данных не у каждой заявки есть запись из всех источников. Например, `credit_card_balance` покрывает только 28,26% заявок train. EDA также обнаружил дочерние записи без соответствующих ключей в предоставленных родительских таблицах: 3 120 184 строки `bureau_balance` и 1 250 826 строк `installments_payments`. Такие несовпадения не означают автоматически порчу данных; требуется явно определить правила обработки отсутствующих связей. Не удалять все заявки без истории.
- **Временные ограничения:** Исключать события, недоступные на момент текущей заявки, и проверять относительные даты и даты обновлений, в частности `DAYS_CREDIT_UPDATE > 0`. Риск утечки нужно проверить, а не объявлять доказанным по одному названию поля. Подготовку агрегатов и их отбор следует выполнять так, чтобы не использовать ответы независимой тестовой выборки для подбора признаков.

**Кандидат конфигурации: не формируется.** Пользователь не сформулировал целевой результат и не выбрал постановку ML-задачи. Нужно исправить метод соединения и уточнить, что обучать. `TARGET`/`binary` можно предложить как возможный вариант после изучения данных, но не как готовую конфигурацию по этому запросу.

## 4. Критерии проверки агента

- **Обязательные результаты:** агент отклоняет прямое объединение с размножением заявок, различает `SK_ID_CURR`, `SK_ID_PREV` и `SK_ID_BUREAU`, предлагает агрегацию историй до одной строки на текущую заявку, не теряет заявки без истории и не приписывает пользователю неназванный таргет.
- **Допустимые альтернативы:** предложить план подготовки таблиц по источникам с контролем количества строк, показать вариант однострочной схемы признаков, уточнить целевую переменную до обучения; использовать разные допустимые агрегации исторических показателей при соблюдении времени событий.
- **Критические ошибки:** считать повторенные после join заявки независимыми наблюдениями; многократно копировать `TARGET` без предупреждения; соединять таблицы по несоответствующим уровням идентификаторов; автоматически удалить все заявки без отдельных историй; считать неполный набор ключей доказательством повреждения данных; выдавать финальный JSON без определения задачи.
