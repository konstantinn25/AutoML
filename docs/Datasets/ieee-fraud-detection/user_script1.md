# IF-01 - Оценка риска мошенничества до антифрод-решения

**Датасет:** IEEE-CIS Fraud Detection (`train_transaction.csv`, `train_identity.csv`)  
**Категория:** длинный, бессвязный, посторонняя информация  

## 1. Входные данные

**Запрос пользователя:**

> «Слушай, у нас в платёжном отделе опять обсуждают подозрительные операции. Руководитель хочет понимать, какие платежи стоит отправлять на дополнительную проверку ещё до принятия решения. Ему, конечно, нужны красивые цифры в отчёте, но это отдельный разговор. Я нашёл несколько файлов с транзакциями и сведениями об устройствах. У части платежей дополнительных сведений вообще нет, а поля называются какими-то кодами. Можем по тому, что известно на момент операции, оценивать риск мошенничества? Главное, не выдавать информацию из будущего за признак.»

**Вход для будущего теста:** исходные `train_transaction.csv` и `train_identity.csv` вместе с приведённым выше текстом. Конкурсные `test_transaction.csv` и `test_identity.csv` не требуются для ручного разбора запроса.

## 3. Ручное решение и конфигурация

- **Задача:** После проверки данных сопоставить мошенничество со столбцом `isFraud`, `problem_type = "binary"`, положительным классом `1`. По EDA мошеннические операции составляют 20 663 из 590 540 (3,50%). Важны показатели качества для редкого класса, а не только `accuracy`.
- **Подготовка данных:** Сопоставить `train_transaction.csv` с `train_identity.csv` по `TransactionID`, предварительно проверив уникальность ключей. Использовать левое соединение с сохранением всех транзакций. Данные `identity` доступны только для 144 233 операций (24,42%); их отсутствие не является основанием удалить остальные 446 307 строк. Сохранить информацию об отсутствии дополнительных сведений как потенциально значимую особенность данных.
- **Признаки и момент прогноза:** Не использовать `TransactionID` как предиктор. Проверить, доступны ли поля `identity` и анонимизированные группы `C*`, `D*`, `M*`, `V*` до принятия решения. Само по себе сильное статистическое отношение признака к таргету не доказывает утечку. Если момент появления важных полей нельзя подтвердить, запросить сведения о них или ограничить набор признаков; не объявлять все поля допустимыми.
- **Метрика и валидация:** `roc_auc` возможна как вспомогательная начальная метрика ранжирования риска, но пользователь её не называл. Порог направления на проверку зависит от стоимости ошибок и объёма проверок и не должен назначаться произвольно. Из-за временной структуры `TransactionDT` желательно выделить внешнюю более позднюю оценочную часть размеченной истории. Внутренний режим `auto` не обеспечивает временную проверку автоматически.

**Кандидат конфигурации** (условный, после проверки доступности признаков на момент операции и подготовки одной таблицы):

```json
{
  "label": "isFraud",
  "problem_type": "binary",
  "positive_class": 1,
  "eval_metric": "roc_auc",
  "ignored_columns": [
    "TransactionID"
  ],
  "validation_procedure": "auto",
  "presets": "medium_quality"
}
```

Выбранная метрика - решение конфигурирования, а не извлечённое из запроса требование. Внешний временной тест, соединение таблиц и проверка доступности полей выполняются на уровне сервиса, а не через `ignored_columns` или `validation_procedure`. `time_limit` устанавливается сервисом по умолчанию. Если сведения недоступны до антифрод-решения, окончательная конфигурация формируется только для подтверждённого набора признаков.

## 4. Критерии проверки агента

- **Обязательные результаты:** агент выделяет бизнес-цель и момент принятия решения, определяет `isFraud`/`binary` и класс `1` после просмотра данных, сохраняет транзакции без `identity`, обосновывает соединение по `TransactionID`, учитывает дисбаланс и не использует неподтверждённо доступные признаки.
- **Допустимые альтернативы:** другая обоснованная метрика классификации и иная проверяемая схема работы с пропусками; уточнение о моменте доступности `identity` и анонимизированных полей; остановка до подтверждения критичных сведений. Точное совпадение выбранной вспомогательной метрики с эталоном не обязательно.
- **Критические ошибки:** удалить все операции без `identity`; соединить таблицы с потерей или размножением транзакций; принять корреляцию `V200` за доказанную утечку либо, наоборот, без проверки считать все анонимизированные поля доступными; использовать `TransactionID` как обычный признак без обоснования; назначить произвольный бизнес-порог или выдать случайное разбиение за проверку на будущем периоде.
