# IF-02 - Минимизация стоимости ложных блокировок и пропущенного фрода

**Датасет:** IEEE-CIS Fraud Detection (`train_transaction.csv`, `train_identity.csv`)  
**Категория:** стоимость ошибок  

## 1. Входные данные

**Запрос пользователя:**

> «Лишняя блокировка честного платежа стоит нам условно 80 рублей, а пропущенный фрод - 2400. Мне не нужна просто высокая accuracy. Хочу минимизировать потери по этим двум ошибкам.»

**Вход для будущего теста:** исходные `train_transaction.csv` и `train_identity.csv` вместе с приведённым выше текстом.

## 3. Ручное решение и конфигурация

- **Задача:** `label = "isFraud"`, `problem_type = "binary"`, положительный класс `1` - мошенничество. По EDA его доля составляет 3,50%. Блокировка честного платежа соответствует `FP`, пропущенное мошенничество - `FN`.
- **Стоимость ошибок:** Основной бизнес-критерий - `80 × FP + 2400 × FN` условных рублей на оценочной выборке при заданном правиле блокировки. Он извлекается из `requirements.business_objective`, а не из поля `metric`. Цена `FN` в 30 раз выше цены `FP`. `accuracy`, `roc_auc` и `recall` не являются прямой заменой этой функции.
- **Метрика и порог:** Пользователь не указал ML-метрику. Для предварительного выбора моделей допустима `roc_auc`, если система отдельно считает денежную стоимость. По вероятностям мошенничества нужно подобрать порог решения на валидационных данных и сравнить фактические затраты. Не выбирать порог по финальному тесту и не обещать минимум затрат без отдельной проверки; если такая логика ещё не реализована, прямо сообщить об ограничении.
- **Данные и проверка:** Сопоставить таблицы по `TransactionID`, не теряя операции без `identity`; не использовать идентификатор как признак. Для независимой оценки приоритетен более поздний размеченный период по `TransactionDT`. Распределение мошенничества и полнота `identity` меняются со временем, поэтому нельзя без доказательств переносить результаты случайного разбиения на будущие транзакции.

**Кандидат конфигурации** (для предварительного выбора модели; денежная цель и порог обрабатываются отдельно):

```json
{
  "label": "isFraud",
  "problem_type": "binary",
  "positive_class": 1,
  "eval_metric": "roc_auc",
  "ignored_columns": [
    "TransactionID"
  ],
  "validation_procedure": "auto",
  "presets": "medium_quality"
}
```

`eval_metric = "roc_auc"` не реализует целевую функцию `80 × FP + 2400 × FN`. В дополнение нужен расчёт стоимости и выбор порога вне стандартного списка параметров финальной конфигурации. Если сервис не умеет выполнять эту процедуру, нельзя считать требования пользователя выполненными. `time_limit` задаётся сервисом; независимую оценку и подбор порога проводят на разных частях размеченных данных.

## 4. Критерии проверки агента

- **Обязательные результаты:** агент определяет `isFraud`/`binary` и класс `1`, оставляет `metric` неопределённым при извлечении требований, сохраняет денежную цель отдельно в `requirements.business_objective`, правильно сопоставляет `FP = 80` и `FN = 2400`, отделяет функцию потерь от `eval_metric` и не использует финальный тест для настройки порога.
- **Допустимые альтернативы:** другая обоснованная вспомогательная метрика; расчёт затрат и сравнение порогов вне AutoGluon, либо объяснение, почему текущая версия сервиса не может гарантировать оптимизацию денежных потерь.
- **Критические ошибки:** перепутать цены `FP` и `FN`; записать денежную функцию как название поддерживаемой метрики AutoGluon или потерять её при анализе запроса; выдать `roc_auc`, `recall` или `accuracy` за непосредственную минимизацию денежных потерь; выбрать порог по финальному тесту; игнорировать дисбаланс классов или заявить об экономическом оптимуме без расчёта стоимости.
