# AV-04 - Временная проверка и новые продавцы при ограниченном обучении

**Датасет:** Avito Demand Prediction (`train.csv`, `test.csv` и вспомогательные CSV)  
**Категория:** длинный, ограничения, временная и групповая проверка  

## 1. Входные данные

**Запрос пользователя:**

> «Для объявлений, опубликованных позже, хочу отдельную временную проверку по `activation_date`. А ещё интересно, как модель работает на совсем новых продавцах. Обучение не дольше десяти минут, два ядра CPU, без GPU. После запуска покажи, какие признаки модель использовала чаще всего.»

**Вход для будущего теста:** Для будущего теста используются `train.csv`, `test.csv` и приведённый выше текст. Сведения о `user_id` и `activation_date` должны оставаться доступны сервису для организации независимой проверки.

## 3. Ручное решение и конфигурация

- **Задача и таргет:** В размеченной `train.csv` предусмотрена числовая цель `deal_probability`. Регрессия - обоснованный кандидат, если пользователь подтверждает, что требуется прогнозировать спрос именно в таком определении. Если модель предназначена для другой цели, необходимо запросить уточнение. В `test.csv` нет целевых ответов; её нельзя использовать для подсчёта качества.
- **Временная проверка:** Создать независимое хронологическое разбиение по `activation_date`. В EDA показана возможная граница `2017-03-26` (1 162 063 строк до даты, 341 361 начиная с неё); это иллюстрация, а не обязательный порог. Не перемешивать записи для утверждения качества на будущих датах. `validation_procedure = "auto"` задаёт иной, внутренний режим и не заменяет внешнюю временную проверку.
- **Новые продавцы:** Дополнительно провести оценку на `user_id`, отсутствующих в обучении. В иллюстративном временном разбиении 46 145 продавцов встречаются в обеих частях, поэтому временная оценка не доказывает качество на новых продавцах. Можно подготовить отдельный групповой тест и/или отдельно выделить подмножество новых продавцов во временном тесте с проверкой достаточного объёма и репрезентативности. Такое подмножество не равно случайному групповому тесту. `user_id` использовать для разбиения, но не передавать как обучающий предиктор без обоснования.
- **Признаки:** Для сценария публикации контролировать доступность текста, цены, категорий, `image_top_1` и календарных признаков на дату размещения. Не включать будущие периоды активности. `item_id` - идентификатор объявления, исключить из модели.
- **Ограничения:** Установить `time_limit=600`, `num_cpus=2`, `num_gpus=0`. Лимит `time_limit` относится к обучению AutoGluon, а не ко времени всей подготовки, построению независимых тестов и расчёту отчётов. `presets=medium_quality` - проектный базовый выбор, а не требование из пользовательского текста.
- **Результаты:** Формулировку «какие признаки модель использовала чаще всего» необходимо уточнить: частота использования признака алгоритмами и его предсказательная важность - разные характеристики. Сервис может предложить `return_feature_importance = true` и расчёт `predictor.feature_importance()` после обучения. Результат измеряет изменение качества при перестановке признака, а не частоту его применения и не причинное влияние. Нельзя выдавать эту метрику за запрошенную частоту без согласования.

**Кандидат конфигурации** (условный; после подтверждения `deal_probability` как цели, выбора корректных внешних проверок и согласования формата отчёта):

```json
{
  "label": "deal_probability",
  "problem_type": "regression",
  "eval_metric": "root_mean_squared_error",
  "ignored_columns": [
    "item_id",
    "user_id",
    "image"
  ],
  "validation_procedure": "auto",
  "time_limit": 600,
  "num_cpus": 2,
  "num_gpus": 0,
  "presets": "medium_quality"
}
```

Для согласованного отчёта о важности признаков в настройках сервиса можно установить `return_feature_importance = true`; это не аргумент `fit()`. Такая настройка не гарантирует требуемую пользователем статистику частоты использования. `ignored_columns` должен содержать только реально присутствующие в подготовленной таблице столбцы. Внешняя временная и групповая проверки выполняются отдельной логикой сервиса. При неразрешённой постановке показанный JSON не является финальной конфигурацией.

## 4. Критерии проверки агента

- **Обязательные результаты:** не приписывать пользователю выбор `deal_probability`, пока он его не подтвердил; предложить числовую цель и регрессию после сопоставления с датасетом; различать проверку на поздних объявлениях и проверку на новых `user_id`; соблюсти `time_limit=600`, `num_cpus=2`, `num_gpus=0`; объяснить, что важность признаков и частота их использования не совпадают; вынести отчёт в настройки сервиса.
- **Допустимые альтернативы:** подготовить два независимых оценочных среза либо отдельный срез новых продавцов внутри хронологического теста при корректном контроле; выбрать другую обоснованную регрессионную метрику; вместо важности признаков согласовать иной отчёт, который реально соответствует запросу.
- **Критические ошибки:** объявить случайное разбиение доказательством качества на будущих датах; смешать объявления одного продавца между train и тестом новых продавцов; считать обычную временную проверку автоматическим тестом на новых продавцах; показывать `feature_importance` как частоту использования без пояснений; рассчитывать качество на неразмеченном `test.csv`; проигнорировать ограничение CPU, GPU или времени.
