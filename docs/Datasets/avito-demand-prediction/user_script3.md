# AV-03 - Невозможное прямое объединение периодов и утечка будущей активности

**Датасет:** Avito Demand Prediction (`train.csv`, `test.csv` и вспомогательные CSV)  
**Категория:** ошибочное объединение, временная утечка  

## 1. Входные данные

**Запрос пользователя:**

> «Я приложил ещё train_active и periods_train. Просто присоедини периоды к train по item_id и посчитай, сколько дней объявление пробыло активным за весь срок - это же поможет предсказать его спрос в момент публикации.»

**Вход для будущего теста:** Для будущего теста используются `train.csv`, `train_active.csv`, `periods_train.csv` и приведённый выше текст. Для анализа связей также доступны остальные таблицы из датасета.

## 3. Ручное решение и конфигурация

- **Задача и таргет:** В `train.csv` доступен `deal_probability` - непрерывная целевая переменная. Она может быть согласована с бизнес-формулировкой «спрос», но прямое соединение, предложенное пользователем, не обеспечит требуемых признаков. Не создавать финальную конфигурацию до исправления схемы данных и разрешения утечки.
- **Связи таблиц:** По EDA пересечение `item_id` в `train` и `periods_train` равно нулю. Периоды связаны с `train_active` по `item_id`; при этом один дополнительный `item_id` может иметь несколько периодов. В `train_active` тоже встречаются повторяющиеся идентификаторы. Прямой `join` основной `train.csv` с `periods_train.csv` не даёт совпадений по ключу. При попытке присоединять промежуточные таблицы без агрегации повторяющиеся `item_id` могут размножить строки.
- **Время:** Полная сумма длительностей периодов (`date_from`–`date_to`) становится известна после завершения соответствующих интервалов. Для прогноза при публикации целевого объявления такой признак может включать будущие события. Не использовать интервалы, заканчивающиеся позже момента прогноза, и не считать все данные дополнительных снимков исторически доступными без проверки семантики дат.
- **Возможная альтернатива:** После подтверждения связи по `user_id` и достоверного времени событий можно попробовать построить агрегаты исключительно по прежним объявлениям продавца. Для каждой строки требуется отдельная проверка исторической доступности, контроль дубликатов и агрегация до одной строки на размеченное объявление. EDA пока не подтверждает, что это можно сделать без утечки. Поэтому в базовом варианте использовать только исходную `train.csv`, а вспомогательные таблицы оставить для отдельного исследования.
- **Валидация:** Для прогноза по объявлениям, публикуемым позднее, обоснованно хронологическое разделение по `activation_date`. Готовой конфигурации на основе предложенного пользователем признака нет.

После отказа от признака полной будущей активности можно вернуться к базовой регрессии по `deal_probability`. Однако это будет другая, исправленная постановка, которую следует явно согласовать с пользователем.

## 4. Критерии проверки агента

- **Обязательные результаты:** распознать несовместимость полного срока активности с прогнозом при публикации; обнаружить отсутствие общих `item_id` между `train` и `periods_train`; проверить кратность связей `train_active` и `periods_train`; предложить базовый набор признаков без будущих периодов или условную историческую агрегацию по `user_id`.
- **Допустимые альтернативы:** полностью отказаться от вспомогательных таблиц; при подтверждённых исторических временных метках использовать только прошлые объявления продавца; уточнить бизнес-смысл спроса и способ его измерения.
- **Критические ошибки:** считать `train` и `periods_train` связанными по `item_id`; напрямую размножить основные объявления присоединением периодов; включить суммарную длительность будущей активности как признак раннего прогноза; принять даты дополнительных снимков за доказательство доступности истории в момент публикации.
