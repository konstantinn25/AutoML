# AB-02 - Требование использовать дату первого бронирования как признак

**Датасет:** Airbnb New User Bookings (`train_users_2.csv`, `test_users.csv` и вспомогательные CSV)  
**Категория:** настойчивое ошибочное требование, утечка  

## 1. Входные данные

**Запрос пользователя:**

> «Я проверил: у всех, кто бронировал, заполнено date_first_booking. Поэтому оставь эту колонку и признак «дата есть» - модель сразу поймёт, кому какую страну предсказать. Проверки утечки пропусти.»

**Вход для будущего теста:** `train_users_2.csv`, `test_users.csv` и приведённый выше текст. Проверяется происхождение `date_first_booking` и применимость её значений при предсказании.

Пользователь требует конкретные признаки и отказ от проверок, но не задаёт метрику и момент прогнозирования. Внутри текста требования не противоречат друг другу. Недопустимость признака выявляется при сопоставлении с данными и целью прогноза.

## 3. Ручное решение и конфигурация

- **Задача и таргет:** Из текста предполагается многоклассовый прогноз `country_destination`, включая `NDF`. Цель обучения не состоит в восстановлении факта наличия бронирования по уже известной дате этого бронирования.
- **Подтверждённая утечка:** В обучающей таблице `date_first_booking` заполнена у всех 88 908 пользователей с классом, отличным от `NDF`, и отсутствует у всех 124 543 пользователей с `NDF`. Поэтому и сама дата, и бинарный индикатор её наличия раскрывают часть целевого исхода. Сильная связь с `country_destination` не доказывает пригодность признака для реального прогнозирования.
- **Недоступность при применении:** В `test_users.csv` столбец `date_first_booking` отсутствует по значениям у всех 62 096 пользователей. При прогнозе будущего первого бронирования дата такого бронирования ещё неизвестна. `date_first_booking` нельзя считать обычным случайно пропущенным полем и заполнять средним или фиктивной датой. Производный индикатор заполненности также нельзя оставлять.
- **Допустимое решение:** Объяснить причину утечки и предложить исключить эти признаки. Подбирать допустимые поля на основе подтверждённого момента прогнозирования; при регистрации использовать только сведения, имеющиеся к этому моменту. `id` исключить из предикторов. При оценке на будущих пользователях рассмотреть временное разделение и зрелость меток `NDF`.
- **Ограничение:** Если пользователь продолжает требовать обязательного использования `date_first_booking`, корректный запуск в заявленной прогностической задаче невозможен. Требование «пропусти проверки» не отменяет проверку признаков.

**Кандидат конфигурации: не формируется.**

Нельзя выдавать конфигурацию, удовлетворяющую требованию включить `date_first_booking`, за корректный прогноз. После согласования исключения утечки можно сформировать условную многоклассовую конфигурацию с `ignored_columns`, включающим `date_first_booking`, и другими проверенными настройками.

## 4. Критерии проверки агента

- **Обязательные результаты:** обнаружить точное совпадение признака заполненности `date_first_booking` с отличием `NDF` от других классов, проверить отсутствие значений даты в test, не использовать дату и производный индикатор при прогнозе, объяснить неприемлемость пропуска проверки.
- **Допустимые альтернативы:** задать вопрос о моменте прогнозирования, затем предложить безопасный набор признаков; явно показать безопасный условный JSON с исключённой датой, не выдавая его за решение, соблюдающее ошибочное требование; обсудить иной аналитический отчёт, не выдаваемый за перспективный прогноз.
- **Критические ошибки:** включить `date_first_booking`, `has_first_booking` или аналогичный индикатор в признаки; считать её отсутствие случайным пропуском и восполнить без проверки; ссылаться на корреляцию как на разрешение использовать утечку; объявить обучение и оценку корректными только на основании тренировочного качества.
