# AB-01 - Первое направление бронирования после регистрации

**Датасет:** Airbnb New User Bookings (`train_users_2.csv`, `test_users.csv` и вспомогательные CSV)  
**Категория:** короткий, бизнес-постановка  

## 1. Входные данные

**Запрос пользователя:**

> «Хочу понимать, куда впервые поедет новый пользователь после регистрации. И тех, кто вообще ничего не забронирует, тоже надо учитывать.»

**Вход для будущего теста:** `train_users_2.csv`, `test_users.csv` и приведённый выше текст. Остальные таблицы датасета доступны для проверки, но не должны автоматически присоединяться к пользовательским признакам.

## 2. Ручной анализ запроса

{

  },
  "metric": {
    "value": null,

  },

Из текста следует прогноз нескольких исходов с отдельным вариантом без бронирования. Точное имя столбца, число классов и смысл `NDF` устанавливаются по данным. Пользователь говорит о поездке, но датасет отражает направление первого бронирования, а не доказанный факт поездки.

## 3. Ручное решение и конфигурация

- **Задача и таргет:** В `train_users_2.csv` присутствует `country_destination`; целевая задача - многоклассовая классификация с 12 классами. `NDF` сохраняется как самостоятельный исход «первое бронирование не зафиксировано», а не как страна и не как доказательство того, что пользователь никогда не забронирует жильё. При необходимости именно факта состоявшейся поездки требуются другие данные. Уточнить горизонт наблюдения, который позволяет считать отсутствие бронирования окончательным.
- **Признаки и момент прогноза:** Использовать только информацию, известную к моменту регистрации. `id` - технический идентификатор и должен быть исключён из признаков. `date_first_booking` и признаки его заполненности недопустимы: наличие даты точно совпадает с отличием `NDF` от остальных классов. Проверить доступность полей регистрации, корректность `date_account_created` и `timestamp_first_active` для выбранного момента. Полный `sessions.csv` нельзя автоматически использовать: для событий нет абсолютных временных меток.
- **Качество данных:** В обучающей таблице 213 451 пользователь; 124 543 (`58,35%`) относятся к `NDF`, 62 376 (`29,22%`) - к `US`, а самый редкий класс `PT` содержит 217 наблюдений. Учесть дисбаланс. Значения `-unknown-` в `gender` и `first_browser` не равны `NaN`. Возраст содержит пропуски и неправдоподобные значения; не заменять их произвольными возрастами без проверки.
- **Метрика:** Для предварительной оценки можно выбрать `f1_macro`, чтобы учитывать качество по редким направлениям, и дополнительно анализировать метрики по классам. Если пользователю нужны хорошо откалиброванные вероятности, допустим иной обоснованный выбор, например `log_loss`. В запросе метрика отсутствует.
- **Валидация:** Для новых регистраций предпочтительно выделить независимых пользователей по `date_account_created` в хронологическом порядке. В EDA приведена иллюстративная граница `2014-04-02`; она не является обязательным параметром теста. Проверить зрелость исходов `NDF` к выбранной границе. `test_users.csv` не содержит целевых ответов и не служит размеченной выборкой для измерения качества.

**Кандидат конфигурации** (после уточнения горизонта для `NDF`, состава признаков и корректной временной проверки):

```json
{
  "label": "country_destination",
  "problem_type": "multiclass",
  "eval_metric": "f1_macro",
  "ignored_columns": [
    "id",
    "date_first_booking"
  ],
  "validation_procedure": "auto",
  "presets": "medium_quality"
}
```

`f1_macro` выбрана на этапе ручного решения, а не извлечена из запроса. Если `id` и `date_first_booking` удалены при подготовке данных, их не нужно повторно перечислять в `ignored_columns`. При формировании любых производных от даты бронирования признаков они также исключаются. `validation_procedure = "auto"` не гарантирует корректную внутреннюю временную валидацию; это отдельная обязанность обёртки. `time_limit` предоставляется настройками сервиса.

## 4. Критерии проверки агента

- **Обязательные результаты:** определить `country_destination` и `multiclass`, сохранить `NDF`, предупредить о различии между направлением бронирования и фактической поездкой, исключить `date_first_booking` и идентификатор, проверить доступность признаков при регистрации, учесть дисбаланс и необходимость хронологической оценки; не выдавать неразмеченный `test_users.csv` за размеченный тест.
- **Допустимые альтернативы:** уточнить фиксированный горизонт для `NDF` до утверждения конфигурации; выбрать другую обоснованную многоклассовую метрику; использовать только проверенные поля регистрации и отказаться от сессионных агрегатов; подобрать другую хронологическую границу с контролем состава классов.
- **Критические ошибки:** удалить `NDF` без изменения и согласования задачи; интерпретировать `NDF` как «никогда не совершит бронирование»; включить `date_first_booking` или её индикатор в признаки; использовать полную историю `sessions.csv` для прогноза при регистрации; измерять качество на тестовой таблице без целевых меток; считать случайное разбиение доказательством качества на будущих регистрациях.
