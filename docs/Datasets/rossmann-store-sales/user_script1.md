# RS-01 - Прогноз завтрашней выручки магазинов

**Датасет:** Rossmann Store Sales (`train.csv`, `test.csv`, `store.csv`)  
**Категория:** короткий, момент прогнозирования  

## 1. Входные данные

**Запрос пользователя:**

> «Сколько каждый магазин заработает завтра? Расписание и план промо известны заранее, а число покупателей - нет.»

**Вход для будущего теста:** `train.csv`, `store.csv`, доступный для анализа `test.csv` и приведённый выше текст. Признаки из `store.csv` необходимо сопоставлять с продажами по `Store`; прогнозная дата и сведения, известные к этой дате, определяют набор допустимых признаков.

## 3. Ручное решение и конфигурация

- **Задача и таргет:** В `train.csv` целевая переменная - `Sales`, дневная выручка магазина. Единица наблюдения - сочетание `Store` и `Date`; эти сочетания уникальны. Подходит `regression`. Для прогноза на завтра необходимо получать одну оценку на магазин и соответствующую дату. `Store` не следует автоматически исключать как бесполезный идентификатор: он обозначает повторно наблюдаемый магазин и может содержать полезную информацию.
- **Признаки и момент прогноза:** Исключить `Customers`: фактическое число покупателей появляется после прогнозируемого дня и отсутствует в конкурсном `test.csv`. Разрешены календарь, магазин, подтверждённое расписание и заранее известные промоакции. `Open` можно использовать только если статус открытия действительно известен на момент формирования прогноза. В конкурсном `test.csv` есть 11 пропусков `Open`; нельзя без проверки заменять их на `0` или считать магазин закрытым. Проверить доступность характеристик из `store.csv` в нужную историческую дату, особенно сведений о конкуренте и `Promo2`.
- **Схема данных:** Присоединить `store.csv` по `Store`: в EDA подтверждён единственный справочный ряд на магазин и наличие соответствующих записей для всех магазинов train/test. Контролировать количество строк после соединения. `test.csv` содержит будущие даты без `Sales`, поэтому предназначен для формирования прогнозов, а не для расчёта локальной метрики.
- **Закрытые магазины:** Нужно уточнить, следует ли предсказывать выручку всех календарных дней или только дней работы. В обучающей истории 172 871 строка с нулевой выручкой; большинство из них - закрытые магазины. Если достоверно известно закрытие на следующий день, нулевая выручка может быть предусмотрена правилом сервиса, но это решение не заменяет согласования постановки. Нельзя безусловно удалять нулевые строки.
- **Метрика и валидация:** Пользователь не задаёт метрику. В качестве базовой допустима `mean_absolute_error`; также возможна `root_mean_squared_error` после согласования важности больших ошибок. Для оценки будущих дней выделить хронологически более поздний размеченный отрезок из `train.csv`. Не перемешивать даты случайно. `validation_procedure = "auto"` относится к внутренней валидации AutoGluon и не обеспечивает временную независимую проверку.

**Кандидат конфигурации** (после подтверждения режима закрытых магазинов, доступности `Open` и плановых признаков, а также корректной временной проверки):

```json
{
  "label": "Sales",
  "problem_type": "regression",
  "eval_metric": "mean_absolute_error",
  "ignored_columns": [
    "Customers"
  ],
  "validation_procedure": "auto",
  "presets": "medium_quality"
}
```

`Customers` исключён как фактический показатель прогнозируемого дня. `Store` сохраняется как признак повторяющегося магазина; `Date` используется для времени и допустимых календарных производных. При включении дополнительных столбцов из `store.csv` нужно проверить доступность значений на дату прогноза. Внешнее хронологическое разбиение и правило обработки закрытых дней выполняет сервис, а не аргумент `validation_procedure`. `time_limit` задаётся настройкой сервиса, поскольку пользователь его не указал.

## 4. Критерии проверки агента

- **Обязательные результаты:** выделить прогноз `Sales` на следующий день по магазинам, определить регрессию; исключить `Customers`; отличить известный график от фактического статуса работы; проверить момент доступности `Open`, `Promo` и сведений из справочника; использовать хронологический тест и уточнить режим закрытых дней; не считать конкурсный `test.csv` источником истинных ответов.
- **Допустимые альтернативы:** предложить RMSE вместо MAE с объяснением; уточнить, известен ли план открытия и для всех ли магазинов нужен прогноз; использовать проверенные исторические лаги продаж при строгом соблюдении временной границы; сформировать условную конфигурацию либо сначала запросить недостающие сведения.
- **Критические ошибки:** использовать `Customers` будущего дня как признак; считать доступность `Open` или исторических условий `Promo2` доказанной без проверки; выбирать случайные строки для теста на будущие дни; автоматически удалять закрытые дни; объявлять отсутствие `Sales` в `test.csv` достаточным для локального подсчёта качества.
