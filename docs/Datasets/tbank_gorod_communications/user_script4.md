# TG-04 - Прогноз заказов транспорта для новых клиентов

**Датасет:** Т-Банк: Коммуникации в Городе (`коммуникации по Городу.csv`)  
**Категория:** длинный, явный, ограничения, групповая валидация  

## 1. Входные данные

**Запрос пользователя:**

> «Нужна модель, которая определяет, был ли заказ в сервисе «Транспорт» в наблюдаемую дату. Хочу проверить, насколько она переносится на клиентов, которых не было в обучении. Используй только признаки, доступные до этой даты; метрика `recall`, обучение максимум 300 секунд, GPU отключить. После запуска покажи сравнение моделей.»

**Вход для будущего теста:** `коммуникации по Городу.csv` и приведённый выше текст. Для подготовки бинарной цели используется `orders_amt_transport`. `id` необходимо сохранить как ключ независимого разбиения по клиентам.

## 3. Ручное решение и конфигурация

- **Задача и таргет:** Для сервиса «Транспорт» имеется `orders_amt_transport`. В подготовленной таблице создать бинарный столбец, например `transport_order_flag = (orders_amt_transport > 0)`. Положительный класс - `1`, задача - `binary`. В EDA 5 871 из 118 189 наблюдаемых строк (4,97%) содержат заказ транспорта. Это статистика наблюдаемой выборки, а не доказанная частота заказов для всех календарных дней и клиентов. Прежде чем обучать модель, подтвердить, что нулевой счётчик в существующей строке означает отсутствие заказа в целевую дату, а не неполный учёт.
- **Момент и признаки:** Пользователь требует сведения только до `business_dt`. Поэтому исключить из признаков все показатели показов, кликов и заказов за саму целевую дату, включая исходный `orders_amt_transport` и показатели остальных сервисов. В файле нет времён отдельных событий, поэтому нельзя утверждать, что дневные счётчики уже были доступны утром или накануне. Допустимы календарные признаки и подтверждённые на тот момент сведения о клиенте (`age`, `gender_cd`, `device_platform_cd`). Исторические агрегаты по `id` формировать только из предшествующих дат. Сам `id` использовать для связи записей и разбиения, не как обычный признак для новых клиентов. Не считать пропущенные даты нулевыми заказами.
- **Групповая проверка:** В файле 8 339 клиентов, у каждого есть несколько строк. Для оценки на невиданных при обучении клиентах требуется независимое разделение по `id` без пересечения клиентов между train и test. Проверить достаточное число положительных исходов в обеих частях. Разделение случайных строк не соответствует требованию. Групповой тест не гарантирует отдельно качество прогноза на будущих датах. При необходимости одновременно проверить оба свойства требуется дополнительный протокол, а внутренняя валидация AutoGluon должна учитывать групповые зависимости.
- **Метрика и ограничения:** Использовать заданную пользователем `recall` для класса `1`. Из-за низкой доли заказов дополнительно контролировать `precision` или число ложных срабатываний в отчёте, не заменяя согласованную метрику. Передать `time_limit=300` и `num_gpus=0`. Время подготовки исторических признаков и внешней проверки не входит автоматически в бюджет `fit()`; при сложной подготовке требуется отдельная оценка времени.
- **Результат и готовность:** После успешного обучения показать leaderboard; в `settings.md` это настройка `return_leaderboard=true`, не аргумент `fit()`. `transport_order_flag` - производный столбец, а не поле исходного CSV. До запуска надо подтвердить определение нулевой метки и подготовить допустимую витрину с историческими признаками и независимым разбиением клиентов. При невозможности подтвердить эти условия агент должен предупредить или остановить запуск.

**Кандидат конфигурации** (после подтверждения смысла нулевой метки, создания среза признаков до целевой даты и корректного разбиения по `id`):

```json
{
  "label": "transport_order_flag",
  "problem_type": "binary",
  "positive_class": 1,
  "eval_metric": "recall",
  "ignored_columns": [
    "id"
  ],
  "validation_procedure": "auto",
  "time_limit": 300,
  "num_gpus": 0,
  "presets": "medium_quality"
}
```

`transport_order_flag` требуется создать из `orders_amt_transport` только после подтверждения полноты учёта заказов. Кандидат предполагает, что из подготовленной обучающей таблицы заранее удалены `orders_amt_transport`, остальные текущие счётчики заказов, показов и кликов, а `id` сохранён только для независимого группового разбиения и исключён из модельных признаков. Если `id` удалён перед `fit()`, его следует убрать из `ignored_columns`. `validation_procedure = "auto"` не обеспечивает само по себе групповую валидацию; соответствующую процедуру необходимо настроить отдельно. `return_leaderboard=true` относится к настройкам сервиса, а не к финальному JSON AutoGluon. В сценарии требуется условный кандидат, а не обещание запуска на необработанном CSV.

## 4. Критерии проверки агента

- **Обязательные результаты:** определить сервис «Транспорт», предложить производную бинарную метку по `orders_amt_transport`, положительный класс `1` и `recall`; установить `time_limit=300`, `num_gpus=0`; сохранить разделение по `id` без пересечений; исключить счётчики целевой даты; проверить полноту нулевой метки и историческую доступность признаков; вывести leaderboard через настройки сервиса либо сообщить об условиях, препятствующих запуску.
- **Допустимые альтернативы:** вместо условного JSON сначала запросить подтверждение полноты учёта заказов; при корректных метках дополнительно показывать `precision` или оценку ложных тревог; выбрать различные воспроизводимые групповые доли train/test при сохранении непересечения клиентов; исключить `id` из витрины заранее вместо `ignored_columns`.
- **Критические ошибки:** перемешать строки и допустить одного клиента одновременно в обучение и тест; использовать `orders_amt_transport` или любые текущие счётчики как предикторы заказа в ту же дату; считать отсутствие строки за день отсутствием заказа; гарантировать корректность нулевых меток без проверки; игнорировать `recall`, 300 секунд или запрет GPU; передавать `return_leaderboard` в `fit()`.
