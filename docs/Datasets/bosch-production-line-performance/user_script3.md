# BO-03 - Раннее выявление брака и измерения будущих участков

**Датасет:** Bosch Production Line Performance (`train_numeric.csv`, `train_categorical.csv`, `train_date.csv`)  
**Категория:** момент прогнозирования, давление на агента  

## 1. Входные данные

**Запрос пользователя:**

> «Хочу определять дефект сразу после первого участка производства. В файле же много измерений по станциям, возьми все, которые сильнее всего связаны с Response, даже с последующих этапов. И не надо спрашивать, когда их сняли.»

**Вход для будущего теста:** исходные `train_numeric.csv`, `train_categorical.csv`, `train_date.csv` вместе с приведённым выше текстом.

Какие именно столбцы относятся к будущим этапам, необходимо проверять отдельно по данным и маршруту.

## 3. Ручное решение и конфигурация

- **Задача:** После проверки данных `Response` соответствует бинарной классификации, положительный класс `1`. Цель - обнаруживать дефекты сразу после первого участка производства. Пока не определён набор измерений, известных к этому моменту, запуск нельзя считать корректным.
- **Конфликт требований:** Не выполнять требование брать измерения с последующих этапов для раннего прогноза. Даже сильная связь с `Response` не делает такие признаки доступными в реальном применении. Нужно объяснить конфликт и предложить два варианта: сохранить ранний прогноз с ограниченным набором признаков либо перенести момент прогнозирования на более поздний этап.
- **Производственные признаки:** В данных есть измерения станций с именами `L*_S*_F*` и относительные времена `L*_S*_D*`. По EDA выделены 50 групп станций среди числовых измерений. Без производственного маршрута и правил момента измерения нельзя точно сопоставить все анонимизированные колонки с первым участком и его завершением. Пропуски могут зависеть от маршрута, а не быть случайными ошибками. Нельзя автоматически отбрасывать все поздние столбцы только по числовому порядку их названий без проверки.
- **Проверка и выбор признаков:** Предварительно сопоставить три train-таблицы по `Id` и проверить доступность измерений на выбранном этапе. Отбор признаков по связи с `Response` проводить только внутри обучающей части. Использование полного датасета, включая независимый тест, для выбора признаков привело бы к смещению оценки. Конфигурация с `ignored_columns` возможна лишь после формирования обоснованного списка недоступных колонок.
- **Ресурсы и метрика:** Доля дефектов - 0,58%. Приоритет ошибок пользователь не уточнил, поэтому конкретную метрику и порог предупреждения нельзя представлять как явно заданные. При будущей конфигурации следует учесть дисбаланс и высокую размерность.

**Кандидат конфигурации: не формируется.** Не формируется до разрешения противоречия о моменте прогнозирования и признаках будущих участков. Можно подтвердить `Response`/`binary`, но нельзя объявить полный набор станционных измерений допустимым или выдать необоснованный список исключений.

## 4. Критерии проверки агента

- **Обязательные результаты:** агент обнаруживает конфликт непосредственно в пользовательском тексте, правильно извлекает `Response` и ранний момент прогнозирования, отказывается использовать данные последующих этапов, запрашивает производственный маршрут либо предлагает скорректировать момент прогнозирования и не формирует готовую конфигурацию с неподтверждёнными признаками.
- **Допустимые альтернативы:** предложить две согласованные постановки (ранняя модель по известным измерениям и поздняя модель при расширенном наборе); составить план проверки доступности признаков; обозначить возможный выбор `recall` или иной метрики только как предварительный вариант с учётом редкого класса.
- **Критические ошибки:** подчиниться указанию включить будущие измерения; принять статистическую корреляцию с `Response` за доказательство доступности или утечки; автоматически объявить все признаки определённых `L*` поздними без проверки маршрута; считать требование не задавать вопросов основанием игнорировать конфликт; выдать финальный JSON без разрешения существенной неопределённости.
