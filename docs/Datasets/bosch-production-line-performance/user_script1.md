# BO-01 - Обнаружение редкого производственного брака

**Датасет:** Bosch Production Line Performance (`train_numeric.csv`, `train_categorical.csv`, `train_date.csv`)  
**Категория:** короткий, бизнес-приоритет  

## 1. Входные данные

**Запрос пользователя:**

> «Не пропускайте бракованные детали на линии. Их мало, но если дефект уйдёт дальше, будет плохо.»

**Вход для будущего теста:** исходные `train_numeric.csv`, `train_categorical.csv` и `train_date.csv` вместе с приведённым выше текстом.

## 3. Ручное решение и конфигурация

- **Задача:** Сопоставить понятие брака со столбцом `Response` после проверки данных. Для него подходят `problem_type = "binary"` и положительный класс `1`. По EDA дефектны 6 879 из 1 183 747 деталей (0,58%). Общая `accuracy` не отражает качество выявления столь редкого класса.
- **Данные:** Сформировать одну строку на деталь из `train_numeric.csv`, `train_categorical.csv` и `train_date.csv`. Соединять по уникальному `Id`, сохранив число деталей и столбец `Response`; не складывать таблицы вертикально. Не использовать `Id` как обычный признак без предметного обоснования. Пропуски по станциям могут быть связаны с маршрутом детали, поэтому механически удалять редкие измерения нельзя.
- **Метрика:** Рассмотреть `recall` для положительного класса `1` как основной показатель приоритета пропущенных дефектов. Одновременно оценивать `precision` и количество ложных предупреждений: максимизация одного лишь `recall` может привести к чрезмерному числу сигналов. Уточнить, сколько ошибочных проверок допустимо и на каком этапе нужно обнаруживать дефект. Не назначать произвольный порог классификации.
- **Признаки и валидация:** Проверить, какие измерения доступны к моменту решения. Без указания этого момента нельзя безусловно разрешить признаки всех станций. По EDA частота брака меняется между последовательными группами деталей; для оценки качества на будущих деталях целесообразна внешняя хронологическая проверка по доступной относительной временной шкале. Внутренний режим `auto` не заменяет такую проверку.

**Кандидат конфигурации** (условный, после уточнения момента прогноза, подготовки общей таблицы и проверки доступности признаков):

```json
{
  "label": "Response",
  "problem_type": "binary",
  "positive_class": 1,
  "eval_metric": "recall",
  "extra_metrics": [
    "precision"
  ],
  "ignored_columns": [
    "Id"
  ],
  "validation_procedure": "auto",
  "presets": "medium_quality"
}
```

`recall` и `precision` выбраны при ручном конфигурировании, а не извлечены из текста как названия метрик. `extra_metrics` относится к отчёту по оценочной выборке. Соединение таблиц, ограничения по моменту прогноза и внешнее разбиение выполняет сервис. `time_limit` берётся из настройки сервиса по умолчанию. До уточнения момента прогноза кандидат не является готовой к запуску конфигурацией.

## 4. Критерии проверки агента

- **Обязательные результаты:** агент определяет `Response`/`binary` и положительный класс `1` после просмотра данных, замечает долю брака 0,58%, приоритет пропущенных дефектов и необходимость контролировать ложные срабатывания; правильно соединяет три таблицы по `Id` и проверяет доступность измерений.
- **Допустимые альтернативы:** иная обоснованная метрика или сочетание показателей для редкого класса; уточнение стоимости ложной проверки и момента прогнозирования; временная или иная обоснованная внешняя проверка в соответствии с применением модели; временная остановка до получения сведений о производственном процессе.
- **Критические ошибки:** выбрать `accuracy` как единственную достаточную метрику; перепутать метки дефекта; соединить таблицы построчно без ключа или размножить детали; удалить все разреженные признаки без анализа; считать измерения любых станций заведомо доступными до момента прогноза; обещать малое число пропусков без контроля ложных тревог.
