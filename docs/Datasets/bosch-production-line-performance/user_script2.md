# BO-02 - Ошибочное объединение производственных таблиц

**Датасет:** Bosch Production Line Performance (`train_numeric.csv`, `train_categorical.csv`, `train_date.csv`)  
**Категория:** ошибочное объединение таблиц  

## 1. Входные данные

**Запрос пользователя:**

> «Для Bosch у меня numeric, categorical и date. Думаю, просто склеим эти три таблицы строка под строкой, а потом обучим на том, что получилось. Везде же примерно одинаковые детали.»

**Вход для будущего теста:** исходные `train_numeric.csv`, `train_categorical.csv`, `train_date.csv` и соответствующие файлы `test_numeric.csv`, `test_categorical.csv`, `test_date.csv` вместе с приведённым выше текстом.

Пользователь предлагает способ объединения исходных данных, но не определяет цель обучения, таргет или метрику. Внутри текста требования совместимы. Ошибка вертикального объединения выявляется при проверке реальной структуры таблиц.

## 3. Ручное решение и конфигурация

- **Задача:** Сначала исправить подход к подготовке данных. Пользователь не сформулировал отдельную задачу прогнозирования и не назвал результат, который нужно предсказывать. По одному запросу нельзя считать `Response` явно выбранным таргетом. После подготовки таблицы можно предложить постановку классификации по `Response` как вариант и запросить подтверждение.
- **Структура таблиц:** В размеченной части каждая таблица содержит по 1 183 747 деталей. `train_numeric.csv` хранит числовые признаки и `Response`, `train_categorical.csv` - категориальные признаки, `train_date.csv` - времена измерений. Эти файлы представляют разные столбцы одних и тех же деталей, а не дополнительные независимые наблюдения. Вертикальная конкатенация увеличила бы число строк и создала несогласованные записи вместо расширения признаков.
- **Корректное объединение:** Использовать `Id` как ключ. Проверить уникальность и покрытие ключей в трёх таблицах, затем выполнить соединение по `Id` с сохранением одной строки на деталь. Не полагаться на одинаковый порядок строк. `Response` взять из `train_numeric.csv` и не копировать его в признаки. В train EDA не обнаружил повторов `Id` в `train_numeric.csv`.
- **Train и test:** Группы `test_numeric.csv`, `test_categorical.csv`, `test_date.csv` соединяются отдельно по тому же принципу. Конкурсный test не содержит `Response` и не должен использоваться для вычисления локальной метрики или как размеченные обучающие строки. Нужно проверить согласованность схем после соединений. `Id` нужен для сохранения соответствия прогнозов деталям, но обычно исключается из набора предикторов.
- **Разреженность:** В группах много пропусков; в категориальных данных есть 163 полностью пустых столбца. Такие столбцы можно рассматривать для исключения после проверки, но нельзя считать все неполные измерения ошибками. Пропуски могут отражать различия производственных маршрутов.

**Кандидат конфигурации: не формируется.** Пользователь не определил ML-задачу. Сначала нужно объединить таблицы по `Id` и согласовать целевой результат. Ошибочную вертикальную конкатенацию нельзя принимать за корректную подготовку для AutoGluon.

## 4. Критерии проверки агента

- **Обязательные результаты:** агент распознаёт неверный способ объединения, предлагает соединять numeric/categorical/date по `Id` в пределах train и test, сохраняет одну запись на деталь, отличает `Response` от признаков и не формирует окончательную ML-конфигурацию без согласования задачи.
- **Допустимые альтернативы:** проверка уникальности `Id` и схемы таблиц до объединения; предложение `Response`/`binary` как возможной постановки после изучения данных, явно обозначенное как предположение; демонстрация правильной структуры объединённой таблицы без фактического запуска обучения.
- **Критические ошибки:** вертикально склеить группы признаков и считать результат корректной обучающей выборкой; присоединить test к размеченным train-строкам; допустить размножение деталей или потерю `Response`; принять `Response` за явно заданную пользователем цель; заявить, что метрика рассчитывается на конкурсном test без ответов.
