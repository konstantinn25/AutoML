# BO-04 - Ограниченное CPU-обучение и проверка на более поздних деталях

**Датасет:** Bosch Production Line Performance (`train_numeric.csv`, `train_categorical.csv`, `train_date.csv`)  
**Категория:** явный, ограничения, временная валидация  

## 1. Входные данные

**Запрос пользователя:**

> «Построй модель для `Response`: `binary`, метрика `roc_auc`, обучение не дольше 10 минут, только CPU. Хочу оценить качество на более поздних деталях, а не на случайно перемешанных строках.»

**Вход для будущего теста:** исходные `train_numeric.csv`, `train_categorical.csv` и `train_date.csv` вместе с приведённым выше текстом. Конкурсные файлы `test_*.csv` не содержат `Response` и не нужны для независимой локальной проверки качества.

## 3. Ручное решение и конфигурация

- **Задача и бюджет:** Сформировать `label = "Response"`, `problem_type = "binary"`, `positive_class = 1`, `eval_metric = "roc_auc"`, `time_limit = 600`, `num_gpus = 0`. `num_cpus` пользователь не ограничивал. По EDA обучающие данные содержат 1 183 747 деталей, из них 6 879 дефектных (0,58%). Десятиминутный лимит не гарантирует обучение всех моделей на многотысячном наборе признаков. При невозможности выполнить качественный запуск нужно сообщить об ограничении, а не обещать результат.
- **Подготовка данных:** Объединить train-таблицы numeric/categorical/date по `Id`, проверив уникальность ключей и сохранение строк. Целевой столбец находится в `train_numeric.csv`. Использовать `Id` только для соединения и сопоставления результатов; исключить его из признаков, если нет отдельного предметного обоснования. Согласовать момент доступности производственных измерений, поскольку пользователь его не указал.
- **Внешняя временная валидация:** Проверить разбиение на ранние и поздние детали по первому известному времени измерения из `train_date.csv`. В EDA такая последовательная группировка используется как приближение к производственному порядку. Времена относительные, не календарные. Для 582 деталей нет известных временных измерений; их нельзя произвольно отнести к позднему периоду. Способ обработки этих деталей и границу разбиения нужно зафиксировать, не изменяя порядок после оценки результата.
- **Внутренняя валидация:** `validation_procedure = "auto"` не гарантирует соблюдения временной последовательности внутри обучения и при отборе модели. Для корректной временной оценки необходимо отдельно обеспечить совместимый механизм внутренней валидации либо явно указать ограничения такого отбора. Не использовать позднюю внешнюю тестовую часть для выбора конфигурации, метрики, гиперпараметров или признаков.
- **Ресурсы и качество:** Из-за большого количества столбцов, крайне высоких долей пропусков и редкого класса ограничение CPU/600 секунд может потребовать ограничения числа моделей или согласованного поднабора обучающих данных. Такие изменения фиксируются отдельно. На независимом временном тесте рассчитывать `roc_auc` только при наличии обоих классов; дополнительно полезно показать показатели для класса `1`, но пользователь явно потребовал именно `roc_auc`.

**Кандидат конфигурации** (условный, после соединения таблиц, подтверждения момента прогноза и согласования корректной временной валидации):

```json
{
  "label": "Response",
  "problem_type": "binary",
  "positive_class": 1,
  "eval_metric": "roc_auc",
  "ignored_columns": [
    "Id"
  ],
  "validation_procedure": "auto",
  "time_limit": 600,
  "num_gpus": 0,
  "presets": "medium_quality"
}
```

Внешнее временное разбиение и объединение источников выполняет сервис до `fit()`. Параметр `validation_procedure` относится к внутреннему режиму обучения и сам по себе не обеспечивает хронологическую проверку. `time_limit = 600` задаёт бюджет `fit()`, а не время объединения, валидации и отчёта. `ignored_columns` применяется обёрткой. Если корректная временная валидация или допустимый состав признаков не обеспечены, эту конфигурацию нельзя считать окончательной.

## 4. Критерии проверки агента

- **Обязательные результаты:** агент извлекает все явные требования (`Response`, `binary`, `roc_auc`, `time_limit=600`, `num_gpus=0`), объединяет три train-таблицы по `Id`, предлагает внешнюю проверку на более поздних деталях по относительному времени и не выдаёт случайное разбиение за временное; учитывает 582 детали без временной метки и вычислительные ограничения.
- **Допустимые альтернативы:** иная обоснованная схема определения раннего/позднего периода по доступным относительным временным измерениям, зафиксированная до обучения; уточнение момента использования модели и допустимого уменьшения выборки/набора моделей; остановка с объяснением, если временная валидация или CPU-ограничение технически не реализуемы.
- **Критические ошибки:** использовать случайное разбиение и представить его как оценку на более поздних деталях; приписать временным измерениям реальные календарные даты; назначить 582 строкам произвольные даты; использовать конкурсный test без `Response` для локального расчёта метрики; игнорировать лимит 600 секунд или запрет GPU; обещать выполнение полного обучения на всех признаках за 10 минут без проверки ресурсов.
